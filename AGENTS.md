# AGENTS.md

Guidelines for AI agents working on jordond.dev - a personal portfolio site built with Astro.

## Project Overview

- **Framework**: Astro v7 (static site generator)
- **Styling**: hand-written CSS, inline in each page's `<style is:global>` block. No CSS framework, no shared stylesheet
- **Language**: TypeScript (strict mode)
- **Package Manager**: bun (v1.4.2)
- **Node Version**: 24+ (compatible runtime; bun is the runtime/package manager)

## Commands

```bash
# Development
bun run dev              # Start dev server
bun run build            # Production build
bun run preview          # Build, then preview with wrangler

# Code Quality
bun run format           # Format all files with Prettier
bun run format:check     # Check formatting without changes
bun run check            # Type-check with astro check

# Testing
bun run test             # Full suite: unit, then smoke, then e2e
bun run test:unit        # Vitest: pure functions and worker logic
bun run test:smoke       # Vitest: parses built dist/ (run `bun run build` first)
bun run test:e2e         # Playwright: runs against wrangler dev (run `bun run build` first;
                          #   first time, also run `bunx playwright install chromium`)

# Data Fetching
bun run fetch-repos      # Fetch GitHub repo data (requires GITHUB_TOKEN)
```

### Pre-commit Hooks

Husky runs `lint-staged` on commit, which auto-formats `*.{ts,css,md,astro}` files with Prettier.

## Code Style

### Formatting (Prettier)

- **No semicolons**: `const x = 1` not `const x = 1;`
- **Trailing commas**: Always use trailing commas in multiline structures
- **Quotes**: Double quotes for JSX attributes, Prettier defaults elsewhere

### Naming Conventions

| Type                | Convention       | Example                            |
| ------------------- | ---------------- | ---------------------------------- |
| Pages               | lowercase        | `index.astro`, `404.astro`         |
| TypeScript files    | camelCase        | `fetch-repos.ts`, `data.ts`        |
| Types/Interfaces    | PascalCase       | `RepoConfig`, `RepoData`           |
| Constants           | UPPER_SNAKE_CASE | `GITHUB_API_BASE`, `DEFAULT_OWNER` |
| Functions/Variables | camelCase        | `fetchRepo`, `languageColors`      |

### Imports

```typescript
// 1. Type imports first (use `import type`)
import type { RepoConfig, RepoData } from "../types/repo"

// 2. External packages
import { writeFileSync } from "fs"

// 3. Internal modules (relative paths, no aliases)
import { repos, GITHUB_API_BASE } from "../config/repos"
```

**No path aliases configured** - use relative imports (`../`, `./`).

### Exports

- **Named exports** for configs, types, utilities, and constants
- **Default exports** only for Astro components (automatic)

```typescript
// Good: Named exports
export const skills = ["Kotlin", "TypeScript"]
export interface CommunityItem { ... }
export type RepoType = "library" | "app"

// Avoid: Default exports in .ts files
export default { ... }  // Don't do this
```

## TypeScript Guidelines

### Type Definitions

Always add JSDoc comments to interfaces:

```typescript
/**
 * Configuration for a repository to feature
 */
export interface RepoConfig {
  /** GitHub username/org */
  owner?: string
  /** Repository name */
  name: string
  /** Whether to feature prominently */
  featured?: boolean
}
```

### Type Safety

- **Never use `as any`** - fix the actual type issue
- **Never use `@ts-ignore` or `@ts-expect-error`** - these hide real problems
- Use `import type` for type-only imports
- Use optional chaining (`?.`) and nullish coalescing (`??`) appropriately

```typescript
// Good
const owner = config.owner ?? DEFAULT_OWNER
const stars = repo?.stargazers_count ?? 0

// Bad
const owner = config.owner as any
```

## Page Patterns

There are no shared components or layouts. Each route in `src/pages/` is a self-contained file: its own `<html>` document, its own inline `<style is:global>` block, and its own content. Nothing is imported from a shared layout or component tree. When adding or editing a page:

- Keep markup, styles, and data-fetching in the one file. Duplication between `index.astro` and `404.astro` (e.g. shared color values) is the accepted tradeoff for "one file, no hidden dependencies."
- Prefer semantic HTML (`<table>`, `<address>`, correct heading levels) over generic `<div>` soup. It's what keeps the retro look accessible and matches the era the design borrows from.
- Do not add client-side JavaScript unless there's a specific justification; the site is zero-JS today, and that's a deliberate constraint (see `CLAUDE.md`), not an oversight.
- Do not reach for a CSS framework or a custom-properties theming system. Colors and spacing are literal values inside the page's `<style>` block.

## Error Handling

Use try-catch with graceful degradation:

```typescript
async function fetchRepo(config: RepoConfig): Promise<RepoData | null> {
  try {
    const response = await fetch(url, { headers })
    if (!response.ok) {
      console.warn(
        `Warning: Failed to fetch ${config.name}: ${response.status}`,
      )
      return null
    }
    return await response.json()
  } catch (error) {
    console.error(`Error: Failed to fetch ${config.name}:`, error)
    return null
  }
}
```

- Return `null` on error instead of throwing (for non-critical operations)
- Use `console.warn` for recoverable issues
- Use `console.error` for actual errors
- Continue processing other items if one fails

## Testing

There are three layers, and `bun run test` runs all of them in order. Every change must keep it green (see `CLAUDE.md`'s Testing Gate).

### Unit (`tests/unit/`, `bun run test:unit`)

Vitest against plain functions. No build or browser needed. Covers the pure transforms in `scripts/lib/repos.ts`, the `workers/nightly` scheduled handler (with `fetch` stubbed via `vi.stubGlobal`), and `getRobotsTxt` from `src/pages/robots.txt.ts`. Add a unit test whenever you add or change a pure function or a Worker's non-network logic.

### Smoke (`tests/smoke/`, `bun run test:smoke`)

Vitest that runs **after** `bun run build` and parses the built `dist/` output with `linkedom`. No browser needed. Checks things like: the title/h1, contact CTAs, populated project tables, in-page anchors resolving, internal links existing on disk, and `robots.txt`/sitemap content. Add a smoke test when you need to assert something about the final rendered HTML that doesn't require a real browser (e.g. "this data always produces at least one row").

### E2E (`tests/e2e/`, `bun run test:e2e`)

Playwright, also run **after** `bun run build`, against `wrangler dev` serving `dist/` on port 8787 (desktop and mobile Chromium projects). Checks real browser rendering, no console/network errors, in-page navigation, the 404 response status, static file serving, and an axe scan for WCAG 2.1 AA violations on `/` and the 404 page. Add an e2e test for anything that depends on the actual Worker/browser behavior: navigation, status codes, or accessibility. First run: `bunx playwright install chromium`.

## CI/CD

`.github/workflows/ci.yml`, job **Check**, runs on push/PR to `main` and is the required status check that gates automerge (see `renovate.json`). Keep the job name stable. Steps: format check, `bun run check` (type check), unit tests, `bun run fetch-repos`, build, smoke tests, then Playwright e2e (with the Chromium browser cached between runs).

Three other workflows handle deployment and are unaffected by the Check gate:

- `deploy.yml` runs on push to `main`: fetch repos, build, `wrangler deploy`.
- `preview.yml` runs on PR: fetch repos, build, upload a Cloudflare preview version, and comment the preview URL on the PR.
- `deploy-nightly-worker.yml` runs on changes under `workers/nightly/`: it deploys that Worker, which cron-dispatches `deploy.yml` nightly so repo star counts stay fresh even if nothing else changes.

## Common Tasks

### Adding a Featured Repository

Edit `src/config/repos.ts`:

```typescript
export const repos: RepoConfig[] = [
  { name: "new-repo", type: "tool" },
  // ...
]
```

`bun run fetch-repos` fetches each entry from GitHub and writes `src/data/repos.json`. Libraries and tools are sorted by stars automatically; there's no manual ordering to maintain beyond this list.

### Adding an App or Tool to `data.json`

Hand-maintained entries (things not fetched purely from a GitHub repo config) live in `src/data/data.json` and are merged in by `scripts/fetch-repos.ts` via `scripts/lib/repos.ts`.

- **Apps** go in the `apps` array, shaped like `LocalApp`: `name`, `description`, `homepage?`, `og_image?`, `open_source` (boolean), `role?`, `links?` (`github`, `play_store`, `app_store`, `windows`, `macos`, `linux`), `topics?`. If `open_source` is true and `links.github` is set, `fetch-repos` pulls live stars and `full_name` from GitHub for that entry. Apps keep the order they're listed in.
- **Tools/libraries** go in `tools`/`libraries` arrays, shaped like `LocalRepo`: `name` plus optional `full_name`, `description`, `html_url`, `homepage`, `stargazers_count`, `language`, `topics`, `image`. These are for projects you want listed without a live GitHub fetch; they're sorted by stars alongside the fetched ones.

Run `bun run fetch-repos` after editing to regenerate `src/data/repos.json`, and add or adjust a unit test in `tests/unit/repos.test.ts` if you changed the merge logic itself rather than just the data.
